# Continuity Update Protocol — Event-Driven

## 1. Operating model

Continuity is updated on meaningful project events, not after every chat message or every file commit. The goal is to keep current state recoverable without creating noisy, repetitive commits or conflicting copies of project truth. The mandatory repository-wide procedure is [REPOSITORY_CHANGE_SYNC_STANDARD.md](./REPOSITORY_CHANGE_SYNC_STANDARD.md), with machine-enforced companion-file rules in [SYNC_IMPACT_MATRIX.yaml](./SYNC_IMPACT_MATRIX.yaml).

There are two update classes:

1. **Machine-observed update:** deterministic Git facts collected by GitHub Actions and the Python updater.
2. **Semantic update:** project meaning, decisions, task progress, acceptance, risk interpretation and next permitted action reviewed by AI and authorized by the Human Owner where required.

The two classes must never be silently mixed.

## 2. Event classification

| Event | Machine action | Semantic action |
|---|---|---|
| Prompt/chat exchange with no repository change | None | Create a checkpoint only if a material decision, blocker, milestone or handoff occurred |
| Commit on a feature branch | No canonical state update | Treat as proposed work; inspect through its PR when relevant |
| PR opened or synchronized | PR validation only; no canonical state change | Review proposal and scope; do not treat as accepted |
| Material change merged/pushed to `main` | Workflow observes paths, commit range and main SHA; opens/updates one continuity PR | AI reviews impact; update relevant project records only with authority |
| Task Contract created/revised/approved | Machine snapshot records the merge event after it reaches `main` | Inspect exact revision, authority, risk and dependencies; update task/handoff if material |
| Validation or CI result | Workflow/check evidence remains attached to the commit/PR | Record actual result and limitations; PASS is not acceptance |
| Human Owner accepts/rejects a decision or deliverable | No semantic inference by updater | Update the canonical Decision Register or acceptance record; then append a handoff checkpoint if material |
| Task completion or milestone transition | Machine snapshot sees repository event | Update project-specific state, verification and acceptance records under their own rules |
| Chat-window handoff | None unless a file is committed | Append a concise handoff entry and refresh the next-chat pointer as needed |

## 3. What updates, and when

| Record | Owner | Trigger |
|---|---|---|
| `BOOTSTRAP.md` | Governance maintainer + Human Owner | Startup sequence or authority rules change |
| `CURRENT_STATE.yaml` / `machine_snapshot` | Python updater | Material main event; machine section only |
| `CURRENT_STATE.yaml` / portfolio and semantic fields | AI draft + Human Owner governance | Accepted project, phase, task or baseline change; never by updater |
| `CONTINUITY_PROTOCOL.md` | Governance maintainer + Human Owner | Event or update policy changes |
| `DECISIONS.md` | Governance maintainer | Canonical decision register location/status map changes; decision itself stays in the project register |
| `SOURCE_MANIFEST.csv` | Governance maintainer | Canonical path, authority or bootstrap requirement changes |
| `HANDOFF_LOG.md` | AI draft + Human Owner review | Meaningful checkpoint, accepted decision, blocker transition, milestone, task completion or session handoff |
| `HANDOFF_TEMPLATE.md` | Governance maintainer | Handoff format changes |
| `BVC_NEXT_CHAT_PROMPT.md` | Governance maintainer | Entry flow or bootstrap path changes |

## 4. GitHub Actions behavior

`.github/workflows/continuity-refresh.yml`:

- Observes pushes to `main` for repository changes.
- Supports a manual `workflow_dispatch` refresh on `main`.
- Runs updater unit tests before creating an update.
- Compares the last observed `main` SHA with the current event SHA, so a missed earlier event can be included in the next refresh.
- Ignores continuity-only changes, its own updater/test/workflow paths and avoids self-triggered refresh loops.
- Updates only `machine_snapshot` in `CURRENT_STATE.yaml`.
- Pushes to the reserved `automation/continuity-refresh` branch and opens or updates one PR against `main`.
- Never pushes to `main` and never changes semantic project state.
- Uses the built-in `GITHUB_TOKEN`; no personal access token is required.

The PR branch is machine-owned. If it contains commits not authored by the workflow bot, the updater stops rather than overwrite the branch. If a repository setting, permission or workflow check prevents the action, report the failure; do not claim a refresh occurred.

A workflow generated by `GITHUB_TOKEN` is not relied upon to trigger another workflow. Validation is run in the generating workflow before it opens/updates the PR. Later human-created PRs also receive the pull-request validation job.

## 5. Idempotence and anti-noise rules

- No material path change means no state rewrite and no PR.
- The updater stores a bounded changed-path list and a truncation flag; it does not dump full diffs or full conversation content.
- `CURRENT_STATE.yaml` is updated only when a new material main range exists.
- The automation refresh branch is reused, but only when all branch-only commits are bot-authored.
- The updater must not alter project status, decisions, task status, completion, acceptance, risk level or source authority.
- The Human Owner reviews and merges the continuity PR. A merge only publishes the machine snapshot, not semantic acceptance of the underlying task.

## 6. Manual and conversational updates

A user can make an important decision in chat without committing a file. GitHub Actions cannot observe that conversation. The assistant must identify the canonical project file that should record the decision and must not claim that the automation has captured it.

For a meaningful chat-only event, prepare the relevant semantic record or a handoff PR under explicit scope/authorization. Do not append every prompt to the log.

## 7. Recovery and verification

- Every update PR must identify the source `main` SHA, changed paths, updater version and review requirement.
- A failed updater or invalid YAML blocks the update PR.
- A missing workflow run is not PASS.
- A machine snapshot is not a substitute for live bootstrap.
- Keep Git history as the audit trail; do not create a duplicate log entry for every commit.

## 8. Cross-executor and worker-switch events

A change of model, provider, chat session, GAIS worker, or IDE is a continuity event when another executor is expected to continue the same task.

| Event | Required action |
|---|---|
| Sender prepares a handoff | Commit and remotely verify a checkpoint; record exact files, checks, blockers, and next action |
| Sender releases writer role | Stop all writes; record RELEASED with time and evidence; active writer becomes NONE |
| Receiver starts | Re-read authority/context; independently verify branch and SHA; inspect actual workspace sync |
| Receiver accepts | Record ACCEPTED with evidence; active writer becomes RECEIVER before any write |
| Quota/session interruption | Recover only the last remotely verified commit; report uncommitted work as local-only or unknown |
| Sync conflict or possible concurrent writer | Stop writes; preserve both states; request Human Owner coordination |
| Material checkpoint | Refresh the handoff record only when it records a meaningful new recovery point |

The receiver must not treat a connected account, visible preview, successful file import, or prior worker report as proof that its own workspace is synchronized. Verify the repository, branch, commit SHA, and actual tool capabilities in the receiving session.

See [CROSS_EXECUTOR_CONTINUITY.md](./CROSS_EXECUTOR_CONTINUITY.md) for lifecycle rules and [CROSS_EXECUTOR_RECOVERY_TEST_PLAN.md](./CROSS_EXECUTOR_RECOVERY_TEST_PLAN.md) for pilot scenarios. The schema and validator are consistency checks, not a distributed lock or task-acceptance engine.


## 9. One-event / one-PR semantic synchronization

For every material approval, Contract revision, prompt publication, GAIS evidence intake, Owner acceptance or learner-status transition, use one focused PR containing the canonical source and all required dependent records. Run `scripts/validate_repository_sync.py` against `SYNC_IMPACT_MATRIX.yaml` before Owner review. Do not split one semantic event across separate register-only PRs.

A feature-branch commit remains a proposal. A merge to `main` publishes the complete semantic transaction. The post-merge machine updater then captures only Git metadata in the global `CURRENT_STATE.yaml`; it does not re-interpret project meaning or rewrite project-specific state.

GitHub Actions cannot observe a decision made only in chat. The assistant must prepare the semantic sync PR after the Owner decision is clear. Repository Actions must be permitted to create pull requests for the reserved machine-snapshot workflow; see the setting requirement in [REPOSITORY_CHANGE_SYNC_STANDARD.md](./REPOSITORY_CHANGE_SYNC_STANDARD.md).
