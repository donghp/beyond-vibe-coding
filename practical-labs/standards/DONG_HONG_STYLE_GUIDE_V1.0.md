# Dong Hong Style — Practical Learning Writing Guide

**Document ID:** BVC-PL-STYLE-001  
**Version:** 1.0.0  
**Status:** Proposed common writing guide  
**Applies to:** Reader-facing content in `practical-labs/`

## 1. The voice

Write as a practical builder sharing what has been tried, what worked, what did not, and what remains to be learned.

The reader should feel guided, not lectured. The author should sound experienced but never pretend to know everything or claim results that have not been verified.

The tone is:
- Natural and approachable.
- Clear and technically responsible.
- Confident about observed facts, careful about uncertain details.
- Humble about limitations and ongoing learning.
- Focused on usefulness, not self-promotion.

## 2. Teaching promise

A person with no programming background should be able to understand:
- What problem they are solving.
- Why the next action matters.
- What exactly to do.
- What they should see.
- How to decide whether it worked.
- What to do when the result differs.

Do not teach code first. Start with the person's need and reveal technical ideas only when they help.

## 3. Writing rules

### Prefer
- Short, direct sentences.
- Everyday words before technical vocabulary.
- One idea per paragraph.
- Action-oriented headings.
- Complete copy-ready prompts and commands.
- Concrete examples based on the project evidence.
- Captions that tell the reader what to inspect.

### Avoid
- Artificially grand claims.
- Dense jargon without explanation.
- Repeated disclaimers that interrupt the lesson.
- Sales language disguised as teaching.
- Statements such as "this always works" unless the claim is supported.
- Calling a generated preview "production-ready".
- Describing a planned feature as implemented.
- Claiming an AI response proves a task is complete.

## 4. A useful lesson rhythm

1. Start with the everyday problem.
2. Show the small outcome the learner will build.
3. Explain only the concepts needed for that outcome.
4. Give one action at a time.
5. Show an authentic result.
6. Ask the learner to verify it.
7. Explain one or two likely mistakes.
8. End with what was learned and one next step.

## 5. Prompt voice

Prompts should speak plainly to the AI, while still specifying:
- Objective.
- Context and source of truth.
- Authorized files and operations.
- Forbidden changes.
- Expected output.
- Acceptance criteria.
- Verification evidence.
- Stop conditions.

Never use friendly wording to hide missing authorization. Natural language and precise boundaries must work together.

## 6. Evidence-aware language

Use these distinctions:

| Label | Use |
|---|---|
| OBSERVED | Directly visible in the real interface or actual artifact |
| VERIFIED | Tested and supported by a recorded result |
| OWNER-CONFIRMED | Explicitly confirmed by the Human Owner |
| UNKNOWN | No supported answer is available |
| NOT VERIFIED | The relevant check has not been performed |
| INFERENCE | Reasoned interpretation, clearly separated from fact |
| PLANNED | Intended future work, not an implemented feature |

A statement can be useful without being certain. Say what is known and what would need to be checked next.

## 7. Book relationship

Mention BEYOND VIBE CODING when it genuinely helps the reader understand the broader method. Keep the reference relevant and unobtrusive. The lesson must deliver practical value even if the reader does not buy the book.

**Build with AI. Learn by Doing. Keep the Human in Control.**
