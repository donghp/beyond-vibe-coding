# Cache and Context Optimization for AI Coding Agents

## 1. Three billable token categories

For the provider billing model used in the case study, distinguish:

1. **Input cache miss** — input not served from cache.
2. **Input cache hit** — input served from cache.
3. **Output** — tokens generated by the model.

For a single pricing tier:

```text
Cost = (Miss × MissPrice + Hit × HitPrice + Output × OutputPrice) / 1,000,000
```

When requests cross Peak and Off-peak periods, calculate each request or usage bucket using the applicable tier. Do not apply one price to a mixed-period dataset unless the source report already does so.

## 2. Prefix caching: what it does and does not mean

DeepSeek documents context caching as automatic and prefix-based. A later request can reuse a matching cached prefix. Semantic similarity alone does not guarantee a hit. Cache retention is not permanent and hit behavior is best-effort.

Official reference: [DeepSeek Context Caching](https://api-docs.deepseek.com/guides/kv_cache/).

A useful conceptual layout is:

```text
[Stable system instructions]
[Stable project rules and compact project context]
[Task contract]
[Current task-specific evidence]
```

This ordering can help maintain a reusable prefix when the client/provider preserves the request structure. However, the developer may not control every message, metadata field, tool definition or internal context segment added by the agent client. Validate with actual usage telemetry rather than assuming that a hand-written prompt completely controls the API prefix.

## 3. Stable prefix design

Good candidates for stable content:
- Durable project instructions.
- Coding conventions that apply broadly.
- Stable architecture summaries.
- Security and authorization rules.
- Output/reporting conventions.

Keep changing content later:
- Current task objective.
- Current error.
- New code excerpt.
- Latest test output.
- Temporary investigation notes.

Avoid:
- Random IDs or current timestamps in otherwise stable prefix sections.
- Reordering stable sections without reason.
- Repeating the same instructions in multiple layers.
- Copying an entire repository into every task.
- Assuming every cached token is useful merely because it is discounted.

## 4. Context selection is separate from cache optimization

Cache optimization reduces the price of eligible repeated input. Context optimization reduces the amount of input the task genuinely needs.

A high cache-hit rate can coexist with an oversized context.

Use a Context Manifest to select:
- Mandatory sources.
- Conditional sources.
- Excluded or obsolete sources.
- Authoritative source of truth.
- Freshness requirements.
- Evidence needed for this task.

Example:

```yaml
context_manifest:
  task_id: AUTH-001
  mandatory:
    - docs/auth-architecture.md
    - standards/security.md
  conditional:
    - docs/database-schema.md
  excluded:
    - docs/legacy-migration.md
    - logs/archive/
  source_of_truth:
    - docs/project-state.md
```

## 5. Input optimization

- Retrieve only files relevant to the task.
- Prefer targeted search and bounded file excerpts over repository-wide dumps.
- Exclude stale logs and generated artifacts unless needed.
- Summarize durable project state in a maintained source document; do not let summaries silently replace authoritative requirements.
- Avoid repeating information already present in the stable context.
- Keep task dependencies explicit.

Do not remove necessary security, architecture or acceptance context just to lower token consumption.

## 6. Output optimization

Ask for outputs appropriate to the task:
- Changed-file list.
- Concise explanation of material changes.
- Test/build results.
- Known limitations.
- Evidence references.
- Unresolved questions.

Avoid returning full source files when a diff is sufficient. Do not impose an arbitrary tiny output limit on architecture, debugging or security work that needs detailed reasoning.

## 7. Agent-loop optimization

A coding agent can use input tokens for system prompts, tool descriptions, previous turns and tool results. High input/output ratios are not automatically inefficient.

Measure:
- API requests per accepted task.
- Tool calls per accepted task.
- Repeated file reads.
- Repeated identical tool output.
- Retry and rework count.
- Accepted outcomes.

Combine or batch steps when it preserves control and verification. Do not combine unrelated high-risk changes into one oversized task.

## 8. Cache and context KPIs

```text
Input Cache Hit Rate = Hit / (Hit + Miss)
```

```text
Input/Output Ratio = (Hit + Miss) / Output
```

```text
Cost per Accepted Task = Total API Cost / Accepted Tasks
```

The first two are descriptive telemetry. The third links spend to engineering outcomes and should be the primary optimization metric.

## 9. Common mistakes

| Mistake | Why it is wrong |
|---|---|
| "Long prompts always cost less because they cache" | Cached tokens remain billable and may include irrelevant context |
| "Similar prompts always hit cache" | Prefix matching is structural, not semantic |
| "Low output means good efficiency" | The agent may be stuck, under-producing, or doing useful tool work |
| "High output means productivity" | Output can be wrong, redundant or unaccepted |
| "Short context is always better" | Missing requirements or constraints can increase rework and risk |
| "Cache hit rate is the only KPI" | It ignores context relevance, output, quality and task acceptance |
